# DueBoard 1.1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:**
- Read due dates from any homework platform launched from Brightspace, through visits in a minimized window.
- Suggest dates found in syllabi.
- Ship a Firefox build. All three go out as release 1.1.0.

**Architecture:**
- A platform registry describes every known platform.
- After each sync, the background:
  - picks homework items that need a date (`dueVisits`);
  - opens their Brightspace launch links one by one in a minimized window (`runVisits`);
  - injects a finder script that reports a due date back by message.
- Results are stored in `captured`, keyed by item, and `buildDashboard` merges them.
- Syllabus rows come from syllabus files (PDF/HTML) and Simple Syllabus pages, through a pure row extractor.
- Firefox is a second WXT target from the same code.

**Tech Stack:**
- WXT 0.21 (MV3), React 19, Tailwind 4, TypeScript 5.9
- Vitest + happy-dom + Testing Library
- New: `pdfjs-dist` (syllabus PDFs), `web-ext` (dev only, Firefox lint)

**Spec:** `docs/superpowers/specs/2026-11-07-dueboard-1.1-design.md` (read it first; section numbers below refer to it)

## Global Constraints

- **Language:** all repository text and UI copy is English. No Chinese anywhere in the repo.
- **Data:** nothing leaves the browser. There is no analytics and no remote code.
- **Read-only:** visits never click, type or submit on a platform page. They only read text.
- **Visit limits:**
  - at most 25 visits per sync
  - 20 s per page to land
  - finder polling for up to 10 s
  - 5-minute total budget per run
- **Visit schedule:**
  - date found: recheck after 24 h
  - no date found: recheck after 24 h, at most 3 times, then only on a manual refresh
  - failed: retry after 6 h
  - date already past: never visit
- **Visit window:** `state: 'minimized'`, `focused: false`. Always closed at the end of a run, on error, and when the budget runs out.
- **Brightspace wins:** a date that comes from Brightspace or another connector always wins over a visited date.
- **Permissions:** required hosts stay `https://purdue.brightspace.com/*`, `https://www.gradescope.com/*` and `https://mylab.pearson.com/*`. Add `optional_host_permissions: ["https://*/*"]`. Request a site only from a user click.
- **Firefox manifest:**
  - `browser_specific_settings.gecko.id = "dueboard@yokiwa.github.io"`
  - `strict_min_version = "128.0"`
  - `data_collection_permissions = { required: ["none"] }`
  - no `offscreen` permission
- **Version:** `1.1.0` in `package.json`. The manifest takes it from there.
- **Commits:** end every commit message with the two attribution lines below. Never put a model name in a commit.
  ```
  Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>
  Claude-Session: https://claude.ai/code/session_01YSmZu67Q1vHhbmVgwmotvG
  ```
- **Checks:** after every task, `npm test` and `npm run compile` both pass.

## Review Focus

1. **A run that dies midway leaves a visible minimized window.** On the next start the window must be closed. Owner: Task 7, test `closes a window left over from an earlier run`.
2. **A single assignment page that shows "Due" and also "Available until" (late deadline)** must yield the Due date, not "nothing". Only several *different* dates under the strongest label count as a list. Owner: Task 4, test `prefers Due over Available until`.
3. **Two courses with homework titled the same ("HW 1")** must not get each other's visited dates. Visited dates are keyed by item, not title. Owner: Task 3, test `visited dates are matched by item key, not title`.
4. **Year rollover.** On Dec 20, "Due Jan 5" means next January. On Jan 3, "Due Dec 30" means last December. Owner: Task 2, test `picks the year closest to now across New Year`.
5. **The Brightspace session expires during a run** (a launch lands on the Purdue login). The run must stop rather than record 25 failures. Owner: Task 7, test `stops at the sign-in page without recording failures`.

Labels:

  ```ts
  export interface FoundDue { title: string; dueAt: string; evidence: string }
  export function findDueUniversal(doc: Document, now: Date): FoundDue | null;
  export function findDueWiley(doc: Document, now: Date): FoundDue | null;
  export function findDue(doc: Document, now: Date, platformId?: string): FoundDue | null; // dedicated, then universal
  export function pageLines(doc: Document): string[];   // visible text, one line per block / table row joined " | "
  // messages.ts
  export type VisitMessage =
    | { type: 'visitFound'; found: FoundDue | null; frameUrl: string; top: boolean }
    | { type: 'visitText'; lines: string[]; frameUrl: string };
  export const FINDER_FILE = '/visit-finder.js';
  // The runner sets these on window before injecting FINDER_FILE:
  // __dueboardPlatform?: string; __dueboardMode: 'due' | 'syllabus'
  export function runFinder(win: Window & { __dueboardPlatform?: string; __dueboardMode?: 'due' | 'syllabus' }, send: (m: VisitMessage) => void, opts?: { pollMs?: number; maxMs?: number }): void;
  ```

`findDueUniversal` rule:
1. Collect the text of visible block elements (skip `script`, `style`, `[hidden]`, `aria-hidden="true"`). Run `findDueMatches` on each.
2. Take the strongest label that has any match.
3. If all matches under that label have the same `dueAt`, return it.
4. If they have different `dueAt` values (a list page), return `null`.

The title is the first `h1`, else `[role=heading]`, else `document.title`, trimmed to 200 characters.

`runFinder` polls every `pollMs` (500) for up to `maxMs` (10 000):
- **due mode:** sends `visitFound` with `found` as soon as `findDue` returns non-null. At timeout, only the top frame sends `visitFound` with `found: null`.
- **syllabus mode:** waits until the text stops changing for 1.5 s (or timeout), then sends `visitText` with `pageLines` (top frame, and any frame with more than 20 lines).
- It sends at most one message per frame.

- Produces:
  ```ts
  export type Trigger = 'auto' | 'manual';
  export interface VisitTarget {
    key: string;              // 'brightspace:topic:123', 'pearson:session', 'syllabus:<ou>'
    title: string; courseId: string; launchUrl: string;
    platform?: string;        // registry id guessed from the title or link
    mode: 'due' | 'session' | 'syllabus';
  }
  export function originAllowed(granted: string[], hostname: string): boolean; // granted = permissions.getAll().origins
  export function dueVisits(store: StoreShape, now: Date, trigger: Trigger, granted: string[]): VisitTarget[];
  export type VisitOutcome =
    | { key: string; status: 'found'; found: FoundDue; host: string }
    | { key: string; status: 'none'; host: string }
    | { key: string; status: 'failed'; reason: 'timeout' | 'closed' }
    | { key: string; status: 'needs_permission'; host: string }
    | { key: string; status: 'text'; lines: string[]; host: string }
    | { key: string; status: 'landed'; host: string }
    | { key: string; status: 'signed_out' };
  export function applyOutcomes(store: StoreShape, targets: VisitTarget[], outcomes: VisitOutcome[], now: Date): Pick<StoreShape, 'captured' | 'visitState'>;
  ```

`dueVisits` rules, applied in this order:
1. `settings.visits === 'off'` → `[]`. `'manual'` with an `auto` trigger → `[]`.
2. **Candidates** are dashboard items (`includeHidden: true`) that:
   - have a `brightspace:topic:*` source key whose raw item has a `launchUrl`;
   - are not submitted or done;
   - have either `dueAt === null` or `dueFrom === 'platform'`.
3. **Skip by platform:** skip a candidate when its title maps to a registry platform whose reader is `fetch` or `none`, or whose hosts aren't granted. Unknown platforms are visited, because the permission is found on landing.
4. **Schedule by `captured[key]`:**
   - no entry → visit
   - `dueAt` already past → skip
   - `dueAt` set and `checkedAt` older than 24 h → visit
   - `misses` < 3 and `checkedAt` older than 24 h → visit
   - `misses` ≥ 3 → visit only on `manual`, and only when `checkedAt` is older than 1 h
   - `failures` ≥ 1 and `checkedAt` older than 6 h → visit
5. **Order and cap:** never-visited first, then oldest `checkedAt`. Cap at 25.
6. **Pearson session:** prepend a `{ key: 'pearson:session', mode: 'session' }` target when `syncMeta.pearson.lastError.reason === 'not_logged_in'` is newer than its `lastSuccess` and `launchLinks(store).pearson` exists.
7. **Syllabus** targets are added in Task 11.

`applyOutcomes` rules:
- `found` → entry with `dueAt`, `evidence`, `via: 'visit'`, `platform: platformByHost(host)?.id ?? host`, misses and failures reset to 0
- `none` → `dueAt: null`, `misses + 1`
- `failed` → `failures + 1`, keeping the previous `dueAt`
- `needs_permission` → host added to `visitState.needsPermission` (deduplicated), entry unchanged
- `signed_out`, `landed` and `text` don't touch `captured`
- every run sets `visitState.lastRun`

  ```ts
  export type Landing = { url: string } | 'closed' | 'timeout';
  export interface VisitApi {
    openWindow(): Promise<{ windowId: number; tabId: number }>;   // about:blank, minimized, unfocused
    navigate(tabId: number, url: string): Promise<void>;
    waitForLanding(tabId: number, timeoutMs: number): Promise<Landing>; // complete AND host !== purdue.brightspace.com, or a sign-in URL
    granted(): Promise<string[]>;
    inject(tabId: number, mode: 'due' | 'syllabus', platform?: string): Promise<void>;
    nextMessage(tabId: number, timeoutMs: number): Promise<VisitMessage | 'timeout'>;
    closeWindow(windowId: number): Promise<void>;
    remember(windowId: number | null): Promise<void>;    // persists visitState.windowId
  }
  export const SIGN_IN = /\/d2l\/login|login\.purdue\.edu|\/idp\/profile\/|duosecurity\.com/i;
  export async function runVisits(targets: VisitTarget[], api: VisitApi, opts?: { perPageMs?: number; finderMs?: number; budgetMs?: number; now?: () => number; onProgress?: (done: number, total: number) => void }): Promise<VisitOutcome[]>;

  export function createBrowserVisitApi(): VisitApi;   // browserApi.ts
  export function deliverVisitMessage(msg: VisitMessage, sender: Sender): boolean;   // browserApi.ts, used by the router
  ```

`runVisits` steps:
1. If `targets` is empty, return `[]` without opening a window.
2. `openWindow`, then `remember(windowId)`.
3. For each target, while the budget remains:
   - `navigate`, then `waitForLanding(perPageMs = 20000)`
   - `'closed'` → `failed: closed` for this and all remaining targets; stop
   - `'timeout'` → `failed: timeout`
   - landing URL matches `SIGN_IN` → `signed_out`; stop the whole run
   - `mode === 'session'` → `landed`
   - landing host not in `granted()` → `needs_permission`
   - otherwise `inject`, then `nextMessage(finderMs + 2000)`:
     - `visitFound` with a date → `found`
     - `visitFound` with `null` → `none`
     - `visitText` → `text`
     - `timeout` → `failed: timeout`
4. Call `onProgress` after each target.
5. In `finally`: `closeWindow` and `remember(null)`. This runs even when a step throws, and when the budget (300 000 ms) runs out; targets left unvisited get no outcome.

In `browserApi.ts`:
- `inject` first runs a `func` that sets `window.__dueboardMode` / `__dueboardPlatform` (all frames), then `files: [FINDER_FILE]` (all frames).
- `nextMessage` resolves from a per-tab queue filled by `deliverVisitMessage`. That function accepts messages only from the current visit tab.
