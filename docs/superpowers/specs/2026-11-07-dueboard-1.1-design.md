# DueBoard 1.1 design: every platform, syllabus dates, Firefox

Date: 2026-11-07 · Status: implemented in 1.1.0 (see section 12) · Builds on [the 1.0 design](2026-11-04-dueboard-design.md)

## 1. Goals

Students reach homework through Brightspace, but the due dates often live only on the platform the course uses:
WileyPLUS, ALEKS, InQuizitive, WebAssign and others. DueBoard 1.0 reads Brightspace, Gradescope and Pearson in the
background. WileyPLUS dates appear only after the student opens each assignment once, and other platforms show
dates only when they copy them into Brightspace.

1.1 has three goals:

1. **Every platform, automatically.** Due dates from any homework platform a course launches from Brightspace show up
   without the student opening anything by hand.
2. **Syllabus dates.** Deadlines written only in a course syllabus appear as suggestions the student can confirm.
3. **Firefox.** The same extension runs in Firefox and is listed on addons.mozilla.org (AMO).

### Success criteria

- For the author's courses, every WileyPLUS homework in Content shows its due date after one sync, with no
  assignment opened by hand.
- An expired Pearson session no longer shows a banner. DueBoard reopens Pearson through Brightspace and reads it.
- A platform DueBoard has never seen (no dedicated code) still gets its due dates when its assignment page prints
  "Due …" with a date.
- Each course with a Simple Syllabus schedule or a syllabus PDF in Content shows its dated work as "From syllabus"
  suggestions.
- The Firefox build passes `web-ext lint`, installs in Firefox 128+, and syncs Brightspace and Gradescope.
- No data leaves the browser. DueBoard never clicks, submits or changes anything on a platform.

## 2. Platforms

### 2.1 Which platforms Purdue courses use

Purdue publishes no list of the platforms students use. This list combines the author's courses, Purdue documents
(department syllabi, the CS instructional handbook, Innovative Learning tool pages) and what large US universities
commonly use.

| Group | Platforms |
|---|---|
| Read in 1.0 | Brightspace, Gradescope, Pearson MyLab & Mastering, WileyPLUS (only when opened) |
| Seen in the author's courses | WebAssign, McGraw-Hill Connect, Macmillan Achieve |
| Named in Purdue documents | ALEKS, Vocareum, Cengage MindTap / OWL, GoReact, Circuit, Vista Higher Learning, Simple Syllabus |
| Reported by students | Norton InQuizitive (and Norton Smartwork) |
| Common elsewhere, likely at Purdue | zyBooks, Top Hat, Perusall, Packback, Hawkes Learning, Sapling, Expert TA, Knewton Alta, PrairieLearn |
| No deadlines (links only) | Piazza, Ed, Kaltura, H5P, iClicker |

The list will never be complete, so the design must not depend on it. Known platforms get a name and an icon. Any
other platform launched from Brightspace is still read (section 3).

### 2.2 Platform registry

One table, `src/core/platformRegistry.ts`, replaces the label lists scattered across `classifyLink`, `platforms.ts` and
Appendix A of the 1.0 design. Each entry has:

- `id` and `label` (e.g. `aleks`, "ALEKS")
- `hosts`: host patterns, e.g. `*.aleks.com`, used for link classification and for the permission request
- `titleKeywords`: words that identify an LTI launch whose URL doesn't show the platform (e.g. "ALEKS")
- `category`: `homework`, `textbook`, `discussion` or `website`
- `reader`: how due dates are read: `fetch` (Gradescope, Pearson: background requests, as in 1.0), `page` (a
  dedicated page finder, section 3.4), or `universal` (the default)

Adding a platform means adding one entry. Everything else (shortcuts, discovery, permission prompts) reads the table.

## 3. Reading any platform: launch visits

### 3.1 Idea

Most platforms have no login of their own. The student gets in through a Brightspace launch, which creates a session
that expires in hours. So DueBoard does what the student would do: it opens the Brightspace launch link, lets the
platform load, reads the due date on the page, and closes it. This happens in a minimized browser window, so the
real browser handles the sign-in flow (LTI 1.1 forms, LTI 1.3 redirects, cookies). The student agreed that
the window may flash briefly in the taskbar or Dock.

### 3.2 What gets visited

The Brightspace connector already lists homework launches in course content (1.0.2 rules: numbered work, unit-plus-
work titles, every launch inside a Homework or Assignments module). A **visit target** is such an item when:

- it has no due date from Brightspace (topic date or calendar event), and
- its platform's site permission is granted (section 3.6), and
- it is due for a visit by the schedule below.

Pearson is also a target when its connector reports `not_logged_in` and a Pearson launch exists. The visit restores
the session, then the Pearson connector runs again in the same sync.

**Schedule (pure function `dueVisits(store, now)`):**

| Item state | Visit when |
|---|---|
| Never visited | Next sync |
| Date found | Again after 24 hours (dates change; one check a day) |
| Visited, no date found | Again after 24 hours, at most 3 times. After that, only on a manual refresh |
| Visit failed (timeout, sign-in page) | Again after 6 hours |
| Date already passed | Never |

At most 25 visits per sync, oldest first. A 30-minute background sync therefore opens the window only when new
homework appears or the daily check is due.

**Setting:** "Read platforms in a minimized window": *Automatically* (default) / *Only when I click Refresh* / *Never*.
Stored as `settings.visits`.

### 3.3 Visit runner

`src/visits/runner.ts`, in the background:

1. Create one window: `windows.create({ url: 'about:blank', state: 'minimized', focused: false })`. Remember its id.
2. For each target, in sequence: navigate the window's tab to the Brightspace launch URL.
3. Wait (up to 20 s) until the tab finished loading on a host other than Brightspace. If it lands on the Purdue
   sign-in page, stop the whole run (Brightspace sign-in is reported by the Brightspace connector as today).
4. If the landing host has no granted permission, record `needsPermission: host` and move on.
5. Inject the finder into every frame: `scripting.executeScript({ target: { tabId, allFrames: true }, func: findDue })`.
   The finder polls the page for up to 10 s, because most platforms are single-page apps that render late.
6. Store the result (section 3.5). Then go to the next target.
7. Close the window when done, on error, and on a 5-minute total budget. If the extension restarts mid-run, the next
   start closes any window it recorded.

The runner never clicks, types or submits. It only reads text. Visits run one at a time, and the existing keep-alive
covers the run.

If the student closes or un-minimizes the window, the run stops quietly and continues next sync.

### 3.4 Finders

A finder is a function `(document, now) → { title, dueAt, evidence } | null` that runs in the platform's page.

**Universal finder** (`src/visits/finders/universal.ts`), for every platform:

- Walk visible text nodes. Find a "due" label (`Due`, `Due date`, `Due:`, `Deadline`, `Closes`, `Available until`)
  followed within 80 characters by a date and time.
- Parse dates with the shared parser `parseDueText` (moved from `capture/wiley.ts` and widened). It handles
  `Nov 10 at 11:59 PM`, `November 10, 2026 11:59 PM EST`, `Monday, Nov 10, 11:59 PM`, `11/10/2026 11:59 PM`,
  `11/10/26 at 11:59pm`, `2026-11-10 23:59` and a date without a time (taken as 11:59 PM local). A missing year
  becomes the one closest to today. US zone abbreviations are converted, otherwise local time is used.
- If several different due dates are on the page, it's a list, not one assignment: return nothing, rather than guess.
- Title: the page's main heading (`h1`, else `[role=heading]`, else `document.title`). It's kept for display and for
  matching only. The Brightspace item keeps its own title.
- `evidence`: the matched text, at most 120 characters. It's shown in the item's details ("Read from ALEKS: 'Due:
  11/10/2026 11:59 PM'") so the student can judge it.

**Dedicated finders** (`src/visits/finders/<platform>.ts`) are added when real page exports exist. 1.1 ships one: the
WileyPLUS finder (the 1.0 `extractWileyDue`). The registry's `reader: 'page'` points at it. A dedicated finder that
finds nothing falls back to the universal finder.

The WileyPLUS content script from 1.0 stays. Opening an assignment by hand still records its date immediately.

### 3.5 Storing and merging

`captured` changes from "keyed by normalized title, Wiley only" to:

```ts
interface CapturedDue {
  itemKey?: string;      // "brightspace:topic:123", set by visits
  title: string;         // page heading, for title matching (1.0 behavior)
  dueAt: string | null;  // null = visited, nothing found
  platform: string;      // registry id, or the landing host for unknown platforms
  via: 'visit' | 'opened';
  evidence?: string;
  checkedAt: string;
  misses?: number;       // consecutive visits that found no date
  failures?: number;     // consecutive failed visits
}
// StoreShape.captured: Record<string, CapturedDue>, keyed by itemKey when present, else "title:" + normalizeTitle(title)
```

A migration moves 1.0 entries to the `title:` keys. `buildDashboard` fills an undated item first from its
`itemKey` entry, then by title, as in 1.0. A Brightspace date always wins over a visited one. The item records
`dueFrom: 'platform'` and the evidence, and the details view shows them.

### 3.6 Site permissions

Reading a platform page needs permission for its site. 1.1 doesn't ask for every site at install. Instead:

- The manifest lists `optional_host_permissions: ["https://*/*"]`. Required host permissions stay as in 1.0
  (Brightspace, Gradescope, Pearson MyLab).
- When a sync discovers launches for a platform in the registry whose hosts aren't granted, the dashboard shows one
  banner: "DueBoard found WileyPLUS and ALEKS in your courses. Allow it to read their due dates? **Allow** · Not now".
  **Allow** calls `permissions.request` for all their hosts at once (a user click is required).
- When a visit lands on a host that isn't in the registry, the banner offers that host by name ("…found
  homework on learn.example.com").
- "Not now" hides the banner for that platform for 7 days. Settings lists the granted platforms with **Remove**.

## 4. Syllabus suggestions

### 4.1 Sources

1. **Simple Syllabus.** Purdue is rolling out Simple Syllabus as each course's "Syllabus" navigation link (from Fall
   2026). DueBoard finds the link in the course navbar (or a content topic launching `*.simplesyllabus.com`) and
   reads it with a launch visit, using the syllabus row extractor (4.2) instead of a due-date finder.
2. **Syllabus files in Content.** Topics titled like `syllabus`, `schedule`, `course calendar` or `important dates`
   that are files stored in Brightspace (PDF or HTML). DueBoard downloads them through Brightspace with the existing
   session, so no extra permission is needed. PDFs are turned into text with `pdfjs-dist`, which is loaded only when
   a PDF is processed. Word files are skipped in 1.1.

Each source is read again only when it changes (Brightspace `LastModifiedDate`) or once a week.

### 4.2 Row extractor

`src/syllabus/extract.ts` is pure and works on lines of text (table rows joined with " | "):

- A row qualifies when it has a date (same parser as 3.4, plus `Mon 11/10`, `Nov. 10` and `10-Nov`) **and** a work
  word: `HW`, `homework`, `assignment`, `quiz`, `exam`, `midterm`, `final`, `project`, `lab`, `essay`, `paper`,
  `report`, `presentation`, `due`.
- Title: the row text without the date, trimmed to 80 characters ("Exam 2", "HW 5 due").
- Time: as written, else 11:59 PM. Exams without a time are all-day.
- A missing year comes from the course's term dates (Brightspace org unit start and end). Rows outside the term are
  dropped.
- "Week 5" or other rows without a calendar date are skipped.

### 4.3 Showing them

- Suggestions are stored per course in `syllabus: Record<courseId, { source, readAt, rows: Suggestion[] }>`.
- A suggestion that matches an existing item (same course, same day, similar title) is not shown.
- They appear in the course details and in the to-do list under **From syllabus**, with **Add** and **Hide**.
  **Add** turns the suggestion into a manual item. **Hide** remembers the dismissal. They are not in the "Next
  deadline" banner or the calendar until added.
- Each suggestion shows where it came from ("Syllabus PDF, page 3: 'Oct 14 — Exam 2'").

## 5. Firefox

- **One codebase.** `npm run build:firefox` and `npm run zip:firefox` (WXT `-b firefox --mv3`). The zip task also
  produces the source archive AMO asks for.
- **Parsing.** Firefox's MV3 background is an event page with a DOM, so `DOMParser` works there directly. A small
  `src/sync/parsers.ts` picks the parser at build time (`import.meta.env.FIREFOX`): the offscreen proxy on Chrome, the
  DOM parsers on Firefox. The Firefox manifest drops the `offscreen` permission and the offscreen page.
- **Manifest.** `browser_specific_settings.gecko`: `id: "dueboard@yokiwa.github.io"`, `strict_min_version: "128.0"`,
  `data_collection_permissions: { required: ["none"] }`.
- **Permission check.** Firefox lets users revoke site access. Before syncing, DueBoard checks
  `permissions.contains` for its required hosts. If one is missing, it shows a banner with **Allow**, which calls
  `permissions.request`. The same check runs on Chrome.
- **Visits** work the same way: `windows.create` with `state: 'minimized'`, plus `scripting.executeScript` with
  `allFrames`.
- **Release.** Each GitHub Release carries the Chrome zip and the Firefox zip. The listing on AMO is public. A new
  guide, `docs/guide/05-firefox.md`, covers the AMO account, upload, source archive, listing and privacy answers.
  Store copy goes in `store/firefox-listing.md`. The install page gets a Firefox section.

## 6. UI changes

- **Item details:** the date's origin ("from Brightspace", "read from ALEKS page · checked 2 h ago", "from
  syllabus") and the evidence text.
- **Banners:** platform permission (3.6) and missing site access (5).
- **To-do and course details:** the "From syllabus" group (4.3).
- **Settings:**
  - "Read platforms in a minimized window" (3.2)
  - granted platforms with **Remove**
  - "Syllabus suggestions" on/off (default on)
- **Sync status:** "Reading 4 platform pages…" while visits run. The popup shows the same line.

## 7. Error handling

| Situation | Behavior |
|---|---|
| Visit lands on the Purdue sign-in page | Stop visits. The Brightspace banner already asks to sign in |
| Platform shows its own sign-in or an error | No date found. Retried per the schedule |
| Page never settles (timeout) | Counted as a failure. Retry after 6 h |
| Several different due dates on one page | Nothing stored (it's a list). Retried per the schedule |
| Student closes the visit window | Run stops. Next sync continues |
| Permission missing for a landing host | Recorded. The banner offers it |
| Syllabus PDF unreadable (scanned image) | Skipped. Course details say "Syllabus couldn't be read" |

## 8. Privacy

- Nothing new leaves the browser. Visits load pages the student is entitled to see, and read only their text.
- Platform site access is optional, asked per platform, and removable.
- Visits appear in the browser history like any page the student opens. This is documented in the privacy policy.
- The privacy policy, the Chrome Web Store permission justifications and the AMO listing are updated for: optional
  site access, launch visits, and reading syllabus files.

## 10. Risks

- **The universal finder misreads a page.** Mitigations: no guess when a page has several dates; evidence shown on
  the item; a Brightspace date always wins; quick dedicated finders from exports.
- **A platform refuses top-level launches** (expects an iframe). The landing page would show an error, so no date is
  found. The item stays undated, the same as today. A dedicated fix can open the Brightspace content page instead.
- **The window flash annoys students.** The schedule keeps visits rare, and the setting allows *Only when I click
  Refresh* or *Never*.
- **Store review of `optional_host_permissions: https://*/*`.** The justification is that each site is requested
  only after it is found in the student's courses, with a click. If review rejects it, fall back to the registry's
  host list.
- **Firefox cookie isolation** might keep the background from using Brightspace cookies. This is checked first in
  the Firefox work. The fallback is to run requests through a visit.
- **Syllabus formats vary widely.** Syllabus dates are suggestions only, never automatic deadlines.

## 12. Changes during implementation

- **Firefox minimum is 140** (not 128): the "collects no data" declaration AMO requires exists from Firefox 140 (Android 142).
- **Launch target read before a visit.** Without the broad `tabs` permission (which would show a "read your browsing history" warning), a browser hides a tab's address on sites DueBoard can't access. So before opening a launch, DueBoard reads the Brightspace launch page to learn which site it goes to, and asks for access instead of visiting when that site isn't allowed.
- **Blocked items wait.** A visit that found no access records the host (`blocked`), and the item is visited again only once that host is allowed, not every sync.
- **One full sync at a time.** A sync asked for while another runs joins it, so there is never more than one visit window.
- **Navigation-bar syllabus links** are checked weekly by the background (stored per course), not by the Brightspace connector.
- **pdf.js** (Mozilla's PDF reader, modern build) runs only in Chrome's offscreen page and in Firefox's background, which is built as a module so pdf.js loads only when a PDF is read.
- To-do rows and the next-deadline banner also name the platform a date was read from.
